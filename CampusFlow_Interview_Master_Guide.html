The 5 Core Features You Built Yourself (Deep Dive)

1. Dynamic Eligibility Evaluation Engine

A decoupled rule-evaluation pipeline that evaluates student credentials against company requirements in real-time:

  • CGPA Check: student.cgpa >= job.minCgpa
  • Backlog Constraint: student.backlogs <= job.maxBacklogs
  • Department Matching: Set intersection of eligible branches.
  • Batch Year: Match graduation year.

Returns a composite EligibilityResult with an overall percentage match score and individual rule evaluations displayed visually in the UI.

2. End-to-End Application State Machine

A strict status lifecycle preventing illegal recruitment transitions:

APPLIED → SHORTLISTED → INTERVIEW_SCHEDULED
        → OFFERED → ACCEPTED / DECLINED
        ↘ REJECTED / WITHDRAWN

Enforced by service-level validation and database constraints (preventing duplicate applications with composite unique key uk_student_job).

3. Spring Security & JWT Filter Chain

Custom JwtAuthenticationFilter extending OncePerRequestFilter. Intercepts incoming requests, extracts the Bearer token, validates HMAC-SHA signature and expiration, extracts user ID and role, and populates SecurityContextHolder.

4. Redis Caching & Invalidation Strategy

Implemented Spring Cache abstraction with Redis. Job listings (GET /api/v1/jobs) and dashboard stats are cached with a 15-minute TTL. Updates or deletions trigger @CacheEvict(allEntries = true) to guarantee cache consistency.

5. Secure Static Resume File Upload Architecture

Engineered resume uploads via MultipartFile with file size limits (5MB) and MIME-type verification (PDF/DOCX). Files are saved to an isolated upload directory with randomized UUID filenames (preventing filename collisions and path traversal attacks). Mapped via Spring's WebMvcConfigurer resource handler to serve files securely over HTTP without exposing the underlying filesystem paths.

Top 15 Technical Interview Questions & Model Answers for CampusFlow

Q1 Why did you use Java 21 and Spring Boot 3 instead of older versions like Java 8/11 and Spring Boot 2?
"Java 21 is a Long-Term Support (LTS) release that introduces Virtual Threads (Project Loom), which provide lightweight concurrency for I/O-heavy enterprise services without exhausting OS thread pools. It also brings Records for boilerplate-free immutable DTOs, Pattern Matching for cleaner polymorphic logic, and Sequenced Collections. Spring Boot 3 aligns with Java 17+ and the Jakarta EE 10 standard, providing native observability with Micrometer, improved startup performance, and GraalVM AOT native image compatibility."
Q2 How does your Dynamic Eligibility Engine work under the hood?
"I created an EligibilityEngine service that decouples business rules from the database entities. When a student views or applies for a job, the engine takes the Student profile and the Job criteria. It evaluates four independent predicates: CGPA threshold, backlog limit, department list containment, and batch year match. Each criterion produces a CriterionEvaluation containing the rule name, expected value, student's actual value, and a pass/fail flag. The engine aggregates these into an EligibilityResult with an overall percentage match score. This modular design makes it easy to add new criteria—such as minimum test scores or specific skill tags—without altering existing application code."
Q3 How do you prevent a student from applying to the same job multiple times?
"Defense-in-depth on two layers. First, at the application service layer, inside a @Transactional method, I execute applicationRepository.existsByStudentIdAndJobId(studentId, jobId) and throw a custom ConflictException if true. Second, at the database layer, the applications table has a composite unique constraint: UNIQUE KEY uk_student_job (student_id, job_id). Even if two concurrent requests bypass the service check simultaneously, MySQL will enforce atomicity and reject the second insert with a unique constraint violation."
Q4 Why did you use DTOs instead of returning JPA Entities directly from controllers?
"Exposing JPA entities directly creates three major problems: 1) Infinite recursion during JSON serialization due to bidirectional relationships (@OneToMany and @ManyToOne), 2) Security vulnerabilities like Mass Assignment / Over-Posting where a malicious payload could overwrite sensitive fields like user.role or company.isVerified, and 3) Tight coupling between the internal database schema and the public API contract. DTOs (Data Transfer Objects) combined with an explicit mapper ensure we only expose the exact fields needed by the client."
Q5 Explain your Spring Security architecture and the JWT authentication lifecycle.
"When a user logs in with email and password, Spring Security's AuthenticationManager verifies credentials via DaoAuthenticationProvider and BCrypt. On success, JwtTokenProvider signs a compact JWT with claims including sub (email), userId, role, and expiration time using HMAC-SHA. On subsequent requests, the client sends this token in the Authorization: Bearer <token> header. My custom JwtAuthenticationFilter (which extends OncePerRequestFilter) intercepts the request, validates the signature and expiration, extracts the user details, creates a UsernamePasswordAuthenticationToken with granted authorities, and stores it in the thread-local SecurityContextHolder."
Q6 How is Redis caching implemented, and how do you handle cache invalidation?
"I used the Cache-Aside pattern via Spring Data Redis. High-frequency read endpoints like GET /api/v1/jobs and placement analytics are annotated with @Cacheable(value = 'jobs', key = '#pageable'). If the key exists in Redis, the response is returned in sub-millisecond time without touching MySQL. To solve the cache invalidation problem, whenever a recruiter creates, updates, or closes a job, the mutating method is annotated with @CacheEvict(value = 'jobs', allEntries = true). We also set a default TTL (Time-To-Live) of 15 minutes to prevent stale data."
Q7 What is the N+1 problem in JPA/Hibernate, and how did you prevent it?
"The N+1 problem occurs when fetching an entity with lazy relationships (e.g. querying 50 Job applications, and Hibernate executes 1 query for the applications, plus 50 separate queries to fetch each associated Student). In CampusFlow, I prevented this by using explicit JOIN FETCH queries in repository methods (e.g., SELECT a FROM Application a JOIN FETCH a.student JOIN FETCH a.job WHERE ...) or using JPA @EntityGraph. This forces Hibernate to retrieve the parent and child records in a single SQL inner or left join."
Q8 How does @Transactional work, and what are its propagation and rollback rules?
"Spring uses AOP (Aspect-Oriented Programming) proxies. When a method annotated with @Transactional is invoked from an external bean, the proxy intercepts the call, opens a JDBC connection transaction, executes the method, and commits on success. By default, Spring rolls back the transaction on unchecked exceptions (RuntimeException and Error), but commits on checked exceptions unless rollbackFor = Exception.class is explicitly specified. The default propagation is REQUIRED (join existing transaction or create new one)."
Q9 How did you handle file uploads securely without exposing server files?
"In StudentService.uploadResume(), I accept a MultipartFile. I validate the content type against an allowlist (PDF, DOCX) and restrict size to 5MB. I strip the user's original filename to prevent Directory Traversal attacks (e.g. ../../etc/passwd) and generate a secure UUID filename like resume_3_a9f1b2c4.pdf stored outside the web root. In WebConfig, I register a ResourceHandler mapping /uploads/resumes/** to the local directory, enabling HTTP streaming while abstracting the real disk path."
Q10 What happens if Redis is down? Will CampusFlow crash?
"In enterprise architectures, caching should be an optimization, not a single point of failure. Spring Cache allows configuring a custom CacheErrorHandler. If Redis is unreachable, the error handler logs a warning and allows the request to fall through directly to the MySQL database. This ensures graceful degradation—the application remains fully functional, albeit with higher database latency."
Q11 How did you handle Global Exception Handling in the backend?
"I created a @RestControllerAdvice class (GlobalExceptionHandler) that intercepts exceptions across all controllers. It maps specific domain exceptions (e.g., ResourceNotFoundException → 404, BadRequestException → 400, BadCredentialsException → 401, AccessDeniedException → 403) to a uniform ApiResponse<T> envelope containing timestamp, status code, error message, and validation field errors for form binding."
Q12 Explain your database indexing strategy in MySQL.
"In addition to primary keys (which automatically create clustered B-Tree indexes), I added secondary indexes on: 1) Foreign keys (student_id, job_id, company_id) to optimize JOIN and WHERE lookups, 2) Search fields like email and usn with unique indexes, and 3) Frequently filtered status columns like applications.status and jobs.is_active. This prevents full table scans during candidate filtering and dashboard aggregation queries."
Q13 Why did you use Axios interceptors in React instead of standard fetch()?
"Axios interceptors provide a centralized pipeline for HTTP operations. In the request interceptor, I read the JWT token from localStorage and automatically attach the Authorization: Bearer <token> header to every outgoing request. In the response interceptor, I inspect error responses: if a 401 Unauthorized status is returned, the interceptor clears the expired token and redirects the user to the login screen with a toast notification. This eliminates repetitive error handling in individual components."
Q14 How does CampusFlow handle role-based authorization at the API level?
"At the network layer, SecurityConfig configures URL matchers (e.g. /api/v1/students/** has role STUDENT, /api/v1/analytics/** has role PLACEMENT_OFFICER or ADMIN). Furthermore, at the controller method level, I enabled @EnableMethodSecurity and used @PreAuthorize('hasRole("RECRUITER")'). This ensures fine-grained role boundaries even if URL patterns change."
Q15 How did you test CampusFlow to ensure reliability?
"I wrote 22 automated tests covering both unit and integration levels. Using JUnit 5 and Mockito, I tested service-layer logic in isolation—verifying eligibility engine boundary conditions, backlog limits, and duplicate application rejections. For end-to-end API verification, I wrote @SpringBootTest integration tests with MockMvc that simulate real HTTP requests through the full filter chain, testing login, recruiter drive access, and placement report generation against an in-memory test database."

3 Distributed Ticketing Engine (Target Project from Email!)

Why Ganglia Technologies Asked About This Project

In their invitation email, the HR Lead specifically noted: "Be ready to walk us through SentimentX or your ticketing engine, and explain the parts you built yourself." This shows they value practical backend engineering, concurrency control, and distributed systems architecture.

Executive Pitch (2 Minutes)

Problem: In high-demand ticketing platforms (like BookMyShow or Ticketmaster), thousands of concurrent users attempt to reserve the same finite pool of seats during a 10-second flash sale window. Traditional relational databases using standard SELECT ... WHERE status = 'AVAILABLE' followed by UPDATE suffer from catastrophic Race Conditions (Check-Then-Act) leading to double-booking, lock contention, and database connection pool exhaustion.

Solution: A high-throughput distributed ticketing engine built with TypeScript, Node.js, Redis, RabbitMQ, and PostgreSQL. It uses atomic Redis Lua scripts for sub-millisecond seat reservations, asynchronous message queues for order persistence, an automated background expiry worker, and Prometheus metrics tracking.

The 4 Core Distributed Components You Built Yourself

1. Atomic Seat Reservation via Redis Lua Scripts

Executed reserve_seat.lua directly inside Redis. Because Redis evaluates Lua scripts atomically in a single-threaded execution context, checking availability, assigning the user ID, and setting a 10-minute hold TTL occurs in O(1) time without distributed locks.

2. Asynchronous Queueing with RabbitMQ & DLQ

Offloaded order creation and payment confirmation to RabbitMQ. If payment processing fails repeatedly, messages are routed to a Dead-Letter Queue (DLQ) with a custom replay script (replay-dlq.ts) ensuring zero message loss.

3. Seat Expiry Worker (TTL Reclamation)

Built ExpiryWorker.ts which runs in the background. If a customer reserves a seat but abandons checkout without paying within 10 minutes, the hold expires and release_seat.lua returns the seat back to the general pool automatically.

4. Sliding-Window Rate Limiter & Prometheus

Engineered a Redis sorted-set (ZSET) sliding-window rate limiter (rateLimiter.ts) to prevent bot scraping and DDoS. Instrumented Prometheus (prom-client) tracking p95 latency, queue depth, and throughput.

Top 10 Technical Questions & Answers for the Ticketing Engine

Q1 Why did you use Redis Lua scripts instead of standard Redis commands or distributed locks?
"If you use separate Redis commands (e.g., GET seat:101 followed by SET seat:101 'RESERVED'), another concurrent request can execute between your read and write, causing a race condition. Distributed locks (like Redlock) introduce network roundtrips, lock expiration edge-cases, and latency overhead. In contrast, Redis executes Lua scripts atomically on its main event thread. No other command or script can run concurrently on that key. This gives us absolute atomicity and sub-millisecond execution with zero locking overhead."
Q2 Walk me through the exact logic inside your reserve_seat.lua script.
"The script takes the seat key (e.g. seat:{showId}:{seatNumber}), user ID, and TTL duration in seconds. It first checks redis.call('GET', seatKey). If the key exists and its value is not null, the seat is already held or booked, so the script immediately returns 0 (failure). If the seat is free, it executes redis.call('SET', seatKey, userId, 'EX', ttl) and returns 1 (success). All of this happens in a single atomic CPU cycle on Redis."
Q3 Why use RabbitMQ instead of writing directly to PostgreSQL?
"Relational databases have strict limits on concurrent active connections (typically 100 to 500 connections in a pool). If 10,000 users checkout simultaneously, direct database writes will cause connection timeouts and crash the DB. RabbitMQ acts as a load leveler (buffer). The API quickly validates the reservation in Redis, publishes an OrderCreated message to RabbitMQ, and returns HTTP 202 Accepted. Consumer workers then process messages at a controlled, sustainable rate, protecting the database."
Q4 What is an Idempotency Key and why is it essential in payment and ticketing systems?
"An idempotent operation can be called multiple times without changing the result beyond the initial execution. In ticketing, if a user clicks 'Pay Now' and a network glitch causes the HTTP response to drop, the browser may retry the request. Without idempotency, the customer might be charged twice. By requiring a unique client-generated Idempotency-Key (UUID) in the request header, we check Redis/DB: if that key was already processed, we return the cached response without re-executing payment or seat booking."
Q5 How does your Dead-Letter Queue (DLQ) work and how do you recover from failures?
"When a worker consumes a message from RabbitMQ and encounters an unrecoverable failure (e.g. database schema mismatch or external payment API timeout after 3 exponential backoff retries), the worker sends a negative acknowledgement (nack) with requeue=false. RabbitMQ automatically forwards this message to our configured Dead-Letter Exchange (DLX) and DLQ. I wrote a maintenance script, replay-dlq.ts, which inspects failed messages, logs root causes, and safely replays them back into the primary queue once the underlying issue is resolved."
Q6 How does the Expiry Worker know when a seat reservation has expired?
"I explored two approaches: Redis Keyspace Notifications (listening to __keyevent@0__:expired) and a time-indexed Sorted Set (ZSET). In production, keyspace notifications can be dropped under high network load because Redis pub/sub does not guarantee delivery. Therefore, I used a Redis Sorted Set where the score is the epoch timestamp of expiration. The ExpiryWorker periodically queries ZRANGEBYSCORE seats_expiring 0 <currentTime>, atomically removes the expired items, and releases the seats back to the inventory pool."
Q7 How does your Sliding Window Rate Limiter work in Redis?
"Fixed-window rate limiters suffer from boundary bursts (e.g. allowing twice the limit across the window edge). In my sliding window algorithm using Redis ZSET, every incoming request adds a member with a unique timestamp as both member and score. We remove all elements older than currentTime - windowSize using ZREMRANGEBYSCORE, and then check ZCARD. If the count exceeds the threshold (e.g. 50 requests per minute), we reject the request with HTTP 429 Too Many Requests. This guarantees a smooth rate regardless of when requests arrive."
Q8 How did you load test this engine and what were the results?
"I wrote an automated TypeScript load test script (load-test.ts) using concurrency promises to simulate 1,000 concurrent virtual users competing for 50 seats simultaneously. Under 1,000 concurrent requests, exactly 50 seats were successfully reserved, 950 received clean 'Seat Unavailable' responses, and zero double-bookings occurred. The average p95 response time for Redis Lua seat reservation was under 12 milliseconds."
Q9 What is the difference between Optimistic Locking and Pessimistic Locking in database terms?
"Pessimistic Locking locks the database record upfront using SELECT FOR UPDATE, preventing any other transaction from reading or writing until the lock is released. It guarantees consistency but kills throughput under high concurrency due to blocking. Optimistic Locking assumes conflicts are rare; it reads without locking, but includes a version column. On write, it checks UPDATE ... WHERE id = :id AND version = :readVersion. If another transaction changed the version, Hibernate throws an OptimisticLockException. In high-concurrency seat booking, we bypass DB locking altogether by using in-memory Redis atomic operations for the reservation phase."
Q10 What Prometheus metrics did you export and why?
"Using the prom-client library, I instrumented four key RED metrics (Rate, Errors, Duration): http_requests_total (labeled by route and status code), http_request_duration_seconds (histogram measuring p50, p90, and p99 latency), active_reservations_gauge (tracking real-time inventory holds), and rabbitmq_queue_depth_gauge. These metrics allow detecting bottlenecks before they cause outages."

4 SentimentX: Multilingual NLP Framework (Target Project from Email!)

Context & Academic Contribution

Major Project: "SentimentX: A Hybrid CNN-XLM-RoBERTa Framework for Multilingual Low-Resource Indian Language Sentiment Analysis". Done under the Department of Information Science & Engineering, Yenepoya Institute of Technology, with team members Naveen Katti, Nikith N, Prem Gouda, and Sumanth T P.

Executive Pitch (2 Minutes)

Problem: Most state-of-the-art sentiment models are trained almost exclusively on English and high-resource European languages. Low-resource Indian languages (Kannada, Hindi, Malayalam, Marathi, Telugu) suffer from complex morphological structures, agglutinative grammar, and heavy phonetic code-mixing (e.g. Kannada typed in English script / 'Kanglish' on social media). Standard models like BERT or standalone LSTMs fail to capture these cross-lingual nuances.

Solution: A novel hybrid deep learning architecture that combines XLM-RoBERTa (cross-lingual transformer encoder) with a 1D Convolutional Neural Network (CNN). XLM-RoBERTa captures global contextual cross-lingual semantics, while the 1D CNN extracts localized spatial n-gram morphological patterns. Trained on 72,365 records across 6 languages, mapping into Ekman's 6 basic emotions (Happiness, Sadness, Anger, Fear, Surprise, Disgust).

Top 8 Technical Questions & Answers for SentimentX

Q1 Why combine a CNN with XLM-RoBERTa? Why not just fine-tune XLM-RoBERTa directly?
"While XLM-RoBERTa's self-attention mechanism is unmatched at learning long-range semantic dependencies and cross-lingual alignments, it processes text at the subword token level. In Indian social media text, users frequently use phonetic spelling variations and informal slang (code-mixing). A 1D Convolutional layer acting on top of the transformer's hidden representations acts as an n-gram feature extractor that detects local morphological character and word patterns regardless of position. Combining both gave us a +7.4% boost in F1-score over baseline multilingual BERT."
Q2 Why did you choose XLM-RoBERTa over Multilingual BERT (mBERT)?
"Two main reasons: Data volume and Tokenization. mBERT was trained on Wikipedia dumps of 104 languages, where Indian languages had very low representation. XLM-RoBERTa was trained on 2.5 Terabytes of filtered CommonCrawl data in 100 languages, providing orders of magnitude more coverage for Indic languages. Furthermore, XLM-RoBERTa uses SentencePiece byte-level BPE with a 250,000 subword vocabulary, significantly reducing Out-Of-Vocabulary (OOV) tokens for Dravidian and Indo-Aryan scripts."
Q3 What specific part did you personally build and contribute to SentimentX?
"I worked on three critical areas: 1) Data Preprocessing & Script Normalization Pipeline: Cleaning noisy social media text, handling zero-width non-joiners in Indic Unicode scripts, and formatting token inputs for the SentencePiece tokenizer. 2) Model Integration & Training: Implementing the hybrid PyTorch architecture that bridges the XLM-RoBERTa pooler output into the 1D CNN and Dense classification head. 3) FastAPI Inference Service: Packaging the fine-tuned model into an asynchronous FastAPI REST microservice that loads the weights onto GPU/CPU and serves sub-50ms inference endpoints for the web client."
Q4 Why is F1-score emphasized more than simple accuracy in this project?
"In emotion analysis, dataset classes are inherently imbalanced. In real-world data, 'Happiness' and 'Anger' appear far more frequently than 'Disgust' or 'Fear'. A naive classifier predicting only the majority class could achieve 80% accuracy while having 0% recall on minority emotions. The Weighted F1-Score balances Precision and Recall across all 6 classes, proving the model truly distinguishes nuanced emotional boundaries."
Q5 How does the Self-Attention mechanism in Transformers work?
"Self-attention allows every word token in a sentence to attend to every other word token, calculating dynamic contextual weights. For an input vector, we project it into three matrices: Query (Q), Key (K), and Value (V). The attention weights are computed using the scaled dot-product: Attention(Q,K,V) = softmax( (Q * K^T) / sqrt(d_k) ) * V. Scaling by sqrt(d_k) prevents vanishing gradients during softmax when the dimension is large."
Q6 What loss function and optimizer did you use during fine-tuning?
"We used Categorical Cross-Entropy Loss combined with the AdamW optimizer (weight decay rate of 0.01) with a linear learning rate warm-up schedule. The initial learning rate was set to 2e-5 for transformer layers and 1e-3 for the newly initialized CNN classification head to prevent catastrophic forgetting of pretrained weights."
Q7 How did you handle code-mixed sentences (e.g. Kannada/Hindi written in English alphabets)?
"Code-mixed text breaks traditional dictionary lookups. Because XLM-RoBERTa's Byte-Pair Encoding operates at the subword and byte level, it breaks Romanized words into phonetically recurring character clusters (n-grams). Our 1D CNN filter then captured these phonetic patterns, allowing the model to recognize sentiment even without standard Devanagari or Kannada orthography."
Q8 How did you optimize the model for production inference in FastAPI?
"Transformer models are computationally heavy. To deploy with low latency, we: 1) Set PyTorch to torch.no_grad() and model.eval() mode to disable autograd graph construction, 2) Applied dynamic 8-bit post-training quantization (reducing model memory by ~50% with negligible loss in accuracy), and 3) Loaded the model weights as a single shared singleton at FastAPI startup using the lifespan context manager."

5 Core CS, Java & Spring Boot Technical Concepts Cheat Sheet

Java 21 Features You Must Mention

  • Virtual Threads (Loom): Lightweight JVM-managed threads (~KB memory) vs OS kernel threads (~1MB). Enables high-throughput thread-per-request model for blocking I/O without reactive programming complexity.
  • Records: Immutable data carriers with compiler-generated getters, equals, hashCode, and toString (public record LoginRequest(String email, String password) {}).
  • Pattern Matching: Enhanced instanceof and switch expressions with exhaustiveness checking.
  • Sealed Classes: Restricting subclass inheritance hierarchy using permits.

Spring Framework Core Concepts

  • Inversion of Control (IoC): Delegating object creation and lifecycle management to the Spring container.
  • Dependency Injection: Passing dependencies into a bean. Always advocate for Constructor Injection because it enables immutability (final fields) and clean unit testing without Spring context.
  • Bean Scopes: singleton (1 instance per container - default), prototype (new instance every request), request, session.
  • Spring AOP: Aspect-Oriented Programming (proxies used by @Transactional, @PreAuthorize, and @Aspect).

Database & SQL Concepts

  • ACID Properties:
    • Atomicity: All operations succeed or all roll back.
    • Consistency: DB transitions between valid states.
    • Isolation: Concurrent transactions don't interfere.
    • Durability: Committed data survives crashes (WAL).
  • B-Tree / B+Tree Indexes: Balanced search tree structure. Leaves contain data or pointers. Logarithmic search O(log N). Speeds up SELECT; slows down INSERT/UPDATE due to tree rebalancing.
  • Transaction Isolation Levels: Read Uncommitted → Read Committed → Repeatable Read (MySQL default) → Serializable. Prevents Dirty Reads, Non-repeatable Reads, and Phantom Reads.

REST & Distributed Systems Fundamentals

  • HTTP Status Codes:
    • 200 OK / 201 Created / 204 No Content
    • 400 Bad Request / 401 Unauthorized (missing/invalid auth)
    • 403 Forbidden (authenticated but lack role permission)
    • 404 Not Found / 409 Conflict (duplicate entry)
    • 500 Internal Error / 503 Service Unavailable
  • JWT Structure: 3 Base64Url parts: Header.Payload.Signature. Signed with secret key. Stateless (server doesn't store session in memory).
